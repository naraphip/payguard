# Simulation Lab requirements

Status **Implemented for local simulation**. Scope follows [FLOW_03 and ER_03](https://drive.google.com/drive/folders/1lKpQdDOkrqpF61vxN_wNN2HHo9NQjNnH), the bundled `SIMULATION_LAB_SPEC.md`, and the [development plan](https://docs.google.com/spreadsheets/d/1bW-Vv10o795JTBwESZnbeY9URWNRkXN3gFVWjCTXX6c/edit) tab `15 SIMULATION LAB`. See the [implementation discussion](../discussions/2026-11-21-simulation-lab.md).

| Area | Acceptance criterion |
| --- | --- |
| Synthetic storefronts | Select flight/hotel or physical/digital goods with booking date or delivery type and quantity. Emit two stages for each account. |
| Checkout contact | Accept an optional synthetic name, email, and phone for the first order. Show the contact captured at successful submission in the evidence for both stages of that order. Keep the full contact in browser memory during the session. |
| Scenario controls | Reproduce normal, fraud ring, and mixed traffic from the seed and configuration. Support 1–100 accounts, 1–60 orders/minute, rotating IPs, shared legitimate Wi-Fi, shared ring device/token, account age, and simulated retries. |
| Replay and ordering | Same seed, configuration, tenant, generator version and HMAC secret reproduce the events and observed account relationships. An identical run ID and configuration return the saved result. Changed configuration under the same ID returns 409. Reversed input is ordered by event time and ID before scoring. |
| Risk and missingness | Redis supplies server-side distinct order counts per stage and entity. Go emits rule hits and typed mock Jev evidence, routes missing payment tokens to review or challenge, and returns `UNSUCCESSFUL` for mock timeouts. |
| Policy attribution | When enabled, `restricted.test` can block flight pre-payments through the demo merchant policy. Preserve platform assessment and action source. Shared IP alone triggers no block. |
| Event decisions and evidence | Select an event to inspect its saved engine action, platform and batch policy actions, final action source, mock Jev result, matching rules, missing signals and 60-second order counts. The UI displays `ALLOW` as Approved, `BLOCK` as Rejected, and `REVIEW`, `CHALLENGE` and `UNSUCCESSFUL` as Review. Batch results are synthetic snapshots. |
| Read saved shared results | Open a shared run by its UUID at `/simulation-lab?run=<uuid>#batch-results` using the saved run GET endpoint. Merchant-scoped runs require their own authenticated run and report endpoints. |
| Shared signal evidence | Match HMAC-derived device, IP and payment token keys by type within the selected run. Compare earlier events by event time and ID. Count each other account once per signal and link to its latest earlier event for that signal. Show the relationship using synthetic event IDs. |
| QA | Scoring sees events and derived signals only. Store synthetic labels and ring IDs in `simulation_qa.ground_truth`. Score payment-stage decisions separately after persisting the run. Report counts, precision, recall and FPR against synthetic labels. |

The optional `config.contactEmailDomain` sent to Go carries only the normalized `.test` domain. It replaces the first order's generated domain at both stages. Without a contact email, the first order keeps its seeded domain. With the demo merchant policy enabled, an exact `restricted.test` match blocks flight pre-payment and records `MERCHANT_POLICY` as the final action source when the assessment succeeds. Other valid test domains pass that policy. The platform decision is reported separately. See the [contact verification steps](../simulation-runbook.md#verify-checkout-contact-and-merchant-policy).

The demo has one local merchant. Production RBAC, live Jev and payment routing, rule activation, adaptive baselines, analyst HOLD, full ER normalization, multi-item carts and cluster scoring are future work. D01–D10 in the source package remain business decisions. The demo timeout and policy rules apply only to synthetic runs.
